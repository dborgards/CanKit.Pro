## 1. Introduction

### 1.1 Purpose of the document

This document specifies the requirements on CanKit for realising, on top of the existing raw-CAN library, a hardened **raw-CAN service layer** and **transport** and **application protocol stacks** built on it. It serves as the binding basis for architecture (`docs/architecture/arc42-CanKit.Pro.md`, written in parallel), implementation and acceptance tests.

### 1.2 Scope

The document specifies:

- **L2 raw-CAN service layer** – the hardening and extension of `ICanBus`/`CanFrame` by multi-consumer demultiplexing, a binding frame ownership contract, TX confirmation, addressing helpers and a uniform threading model per protocol instance.
- **L3 transport layer** – ISO-TP (ISO 15765-2) and J1939-TP (TP.BAM/TP.CM).
- **L4 application protocol layer** – UDS (ISO 14229 over ISO-TP), CANopen (CiA 301), J1939 application (SAE J1939/ISO 11783).

Out of scope: re-implementation of L0 (vendor adapters) and of the already existing L1 core functionality (`ICanBus`, `CanFrame`, `CanRegistry`) – these are taken as given and referenced only where L2 builds on them or where existing defects (see review) justify the L2 requirements.

## 2. Overall Description

### 2.1 Product perspective – layer model

CanKit is structured in five layers. This nomenclature is binding and is used identically in the architecture document:

| Layer | Name | Content | As-is state |
|---|---|---|---|
| L0 | Adapter layer | 7 vendor adapters (SocketCAN, ZLG, PCAN, Kvaser, Vector, ControlCAN, Virtual) + fake-native layer for CI | **existing**, close to production |
| L1 | Raw-CAN core | `ICanBus`, `CanFrame`/`CanFrameView`, `ITransceiver`, `ICanDevice`, `IPeriodicTx`, `CanRegistry`, utilities (`AsyncFramePipe`, `QueuedTxCanBus`, `SoftwarePeriodicTx`, `PreciseDelay`, `BitTimingSolver`) | **existing**, with known defects (see review) |
| L2 | Raw-CAN service layer | Multi-consumer demultiplexing, frame ownership contract, TX confirmation, addressing helpers, threading model per protocol instance, fault/timeout infrastructure | shipped as `CanKit.Pro.RawCan`, `.Actor`, `.Addressing`, `.Reliability` |
| L3 | Transport layer | ISO-TP (ISO 15765-2), J1939-TP (TP.BAM/TP.CM) | both shipped as `CanKit.Pro.IsoTp` and `CanKit.Pro.J1939Tp` |
| L4 | Application protocol layer | UDS (over ISO-TP), CANopen, J1939 (application) | all three shipped as `CanKit.Pro.Uds`, `.CANopen`, `.J1939` |

L2 is the additional "raw-CAN" layer the client asked for: it encapsulates everything several protocol stacks need in common and that does not (or not correctly) exist in L1 today.

### 2.2 Product functions (overview)

- Hardened, multi-consumer-capable access to one physical CAN bus for several simultaneously active protocol instances (e.g. UDS client + CANopen master on the same channel).
- Complete, specification-compliant ISO-TP for diagnostic and generic PDU transfer.
- J1939 transport protocol for PGN-based commercial-vehicle communication.
- UDS client functionality for diagnostic tools/test automation.
- CANopen basic services (SDO, PDO, NMT, heartbeat, EMCY) for automation applications.
- J1939 application layer (PGN/SPN access, address claiming, request PGN).

### 2.3 User/stakeholder characteristics

See section 3.

### 2.4 Constraints (overview)

See section 6 (`CON-xxx`). Central: multi-targeting (`netstandard2.0`, `net10.0`), P/Invoke-based vendor SDKs (upstream in CanKit), platform-dependent timing behaviour.

### 2.5 Assumptions & dependencies

| ID | Assumption/dependency |
|---|---|
| A-1 | The four L2 architecture gaps derived in section 4.1 (frame ownership, demultiplexing, threading model, TX confirm) must be closed before L3/L4 stacks are built productively; L3/L4 requirements in this SRS presuppose a functioning L2. |
| A-2 | *Obsolete.* The ISO-TP prototype was not reused; L3 is rebuilt as `CanKit.Pro.IsoTp`, `IsoTpScheduler` no longer exists. The assumption stays as a record because A numbers are referenced elsewhere. |
| A-3 | J1939-TP is realised as a standalone transport following the same pattern as ISO-TP (own package, static factory, NFR-010). |
| A-4 | Vendor SDK licences (Peak PCANBasic, Kvaser CANlib, Vector XL driver) remain proprietary and are not part of this specification; only the integration points are considered. |
| A-5 | HIL test infrastructure with real hardware is needed for acceptance tests of the L3/L4 layers but is not the subject of this SRS (see section 7). |
| A-6 | `netstandard2.0` remains a target TFM for the core library and L2/L3 in order to support .NET Framework consumers (legacy Windows systems with Kvaser/Vector/PCAN). |

## 4. Functional Requirements

### 4.1 L2 – Raw-CAN service layer (NEW)

The following requirements derive directly from the four architecture gaps identified in the review (review, overall assessment and §2.1–2.3), which must be closed before the protocol stacks (L3/L4) are built.

#### 4.1.1 Frame ownership and lifetime contract

Background: Review §1.5 and §2.1 show that `CanFrame.Dispose()` ignores the `ownMemory` flag and that frames are shared without clear rules between sender, broadcast hub, event handlers and async pipes, leading to use-after-free/double-dispose.

| ID | Requirement | Priority | Verification | Source |
|---|---|---|---|---|
| FR-RAW-001 | The system MUST define a binding, documented frame ownership contract that for every frame hand-over point (TX caller→adapter, adapter RX→event/pipe/hub, hub→multi-consumer) unambiguously states who owns the memory and when `Dispose()` may be called. | Must | Documentation review + architecture decision record; the contract is referenceable in `docs/architecture/arc42-CanKit.Pro.md`. | Review §2.1, recommendation item 2 |
| FR-RAW-002 | The system MUST ensure that `CanFrame.Dispose()` releases the underlying memory only if the frame instance is the owner according to the ownership contract (correction of the defect described in Review §1.5). | Must | Unit test: create a frame with `ownMemory=false`, call `Dispose()`, check that the underlying `IMemoryOwner<byte>` was not disposed. | Review §1.5 |
| FR-RAW-003 | The system MUST give the protocol developer the possibility to consume received frames through a pure read view (`CanFrameView`) without taking on ownership or dispose responsibility. | Must | Unit test: `FrameObserved` handler receives `CanFrameView`; calling `Dispose()` is not possible on the view type (compile-time check). | Review §2.1; existing `CanFrameView` in `ICanBus.FrameObserved` |
| FR-RAW-004 | On multi-consumer broadcast (e.g. virtual bus hub) the system MUST deliver to every consumer an independently viable copy or a reference-counted instance released only after all recipients have consumed it, so that one consumer's dispose does not invalidate the data of other consumers/the sender. | Must | Integration test (virtual loopback): 2 consumers + sender subscribe to the same frame; one consumer disposes immediately, the others continue reading unchanged afterwards. | Review §2.1 (VirtualBusHub use-after-free) |
| FR-RAW-005 | The system SHOULD document and enforce for TX paths that the caller remains owner of the passed frame unless the adapter makes a copy, and that adapters make internal copies before using the frame asynchronously (scheduler queues, echo matching). | Should | Code review checklist per adapter/transport; regression test for ISO-TP scheduler echo matching (Review §2.1, item "Scheduler (ISO-TP)"). | Review §2.1 |

#### 4.1.2 Multi-protocol demultiplexing (subscription/filtering)

Background: Today several protocol instances (e.g. ISO-TP + CANopen) cannot obtain independently filtered views of the same `ICanBus` without taking frames away from each other or blocking callbacks.

| ID | Requirement | Priority | Verification | Source |
|---|---|---|---|---|
| FR-RAW-010 | The system MUST give the protocol developer the possibility to register an independent, filtered frame subscription (ID range, mask or predicate) on a shared `ICanBus` without affecting other subscriptions. | Must | Integration test: 2 subscriptions with disjoint ID filters on the same virtual bus; each receives exclusively the frames matching it. | Review, overall assessment ("multi-protocol demultiplexing") |
| FR-RAW-011 | The system MUST ensure that every subscription owns its own independent buffer/pipe, so that a slow or blocked subscription does not delay the reception of other subscriptions or of the base `FrameObserved` event. | Must | Load test: one subscription processes artificially slowly, the second subscription remains unaffected in latency/throughput. | Derived from the "demultiplexing" architecture gap |
| FR-RAW-012 | The system MUST support orderly un-/re-registration of subscriptions (dispose pattern), so that terminated protocol instances (e.g. ISO-TP channel closed) leave no resources (threads, buffers, hub entries) behind. | Must | Unit test: create and dispose N subscriptions, afterwards resource counters (handles/threads) unchanged compared with the initial state. | Review §2.4 (Virtual: `VirtualBusHub._hubs` leak as negative example) |
| FR-RAW-013 | The system SHOULD provide a default demultiplex strategy for the common case "one 11/29-bit CAN-ID range per protocol instance" (fast path without generic predicate) to avoid overhead at high bus frequency. | Should | Performance test: throughput comparison ID-range filter vs. generic predicate at ≥ 1000 frames/s. | NFR performance, section 5.1 |
| FR-RAW-014 | The system MAY allow the protocol developer to reconfigure subscriptions at runtime (change filter criteria) without recreating the subscription. | Could | Unit test: change filter criterion at runtime, subsequent frames follow the new criterion. | — |
| FR-RAW-015 | The system MUST attach to every subscription element the echo marking reported by the bus and the receive timestamp captured by the adapter, and it MUST deliver echo frames only to subscriptions that explicitly requested them (default: no echoes). | Must | Unit test: bus reports a receive frame and an echo frame; the default subscription receives only the receive frame, `includeEcho: true` receives both with correct `IsEcho`; the timestamp reaches the subscriber unchanged. | [#23](https://github.com/dborgards/CanKit.Pro/issues/23) (review finding Q5) |
| FR-RAW-016 | Built-in subscriptions MUST expose known local buffer overflow through an optional extension compatible with existing `ISubscription` implementations: an independent drop count and ordered frame sequence for conservatively locating capture gaps. Filter/echo exclusions, reads, cancellation and disposal do not count as overflow. Dispatch does not wait for readers; overflow cannot erase the loss metadata itself. Zero local drops do not prove loss-free adapter/driver capture. | Must | Deterministic small-buffer tests: exact evictions, ordering/gaps, independent subscriptions, concurrent writers, exclusions, lifetime and counter boundaries. | [#402](https://github.com/dborgards/CanKit.Pro/issues/402) |

#### 4.1.3 Threading/actor model per protocol instance

Background: Review §1.1 items 9/14 and §2.2/§2.3 show unsynchronised access to shared state (scheduler lists, `_tx` state, timer contexts) from several threads as well as a busy-loop scheduler without a defined concurrency model.

| ID | Requirement | Priority | Verification | Source |
|---|---|---|---|---|
| FR-RAW-020 | The system MUST provide for every protocol instance (e.g. an ISO-TP channel, a CANopen node) a defined, documented threading model that states on which thread/context RX processing, TX scheduling and timeout checking take place. | Must | Architecture review + concurrency test (stress test with ThreadSanitizer equivalent/`Interlocked` counters) without data-race reports. | Review §1.1 items 9, 14; overall assessment "threading model" |
| FR-RAW-021 | The system MUST protect internal state of a protocol instance reachable from several threads (channel registers, timer queues, state machines) against concurrent read/write access (e.g. lock, concurrent collection or single-writer actor). | Must | Unit/stress test: parallel `AddChannel`/`RemoveChannel` and a running processing loop without `InvalidOperationException` on enumeration. | Review §1.1 item 14 (`Router._channels`, `IsoTpScheduler._channels` as `List` without synchronisation) |
| FR-RAW-022 | The system MUST provide an event-driven (not busy-loop-based) scheduling mechanism for periodic/timed protocol tasks (e.g. STmin waits, timeout checks) that blocks when there is no work instead of consuming CPU. | Must | Performance test: CPU utilisation of an inactive channel over 60 s < 1 % (reference value, to be adjusted to the target platform). | Review §1.1 item 9 (100 % CPU busy loop of the `IsoTpScheduler`) |
| FR-RAW-023 | The system MUST pass background exceptions of a protocol instance consistently to the user via a defined channel (event/callback) instead of throwing them on the caller thread of the triggering adapter or losing them as unobserved task exceptions. | Must | Unit test: an artificially triggered background exception is observed via the protocol instance's `BackgroundExceptionOccurred` equivalent, the adapter's RX loop remains unaffected. | Review §1.1 item 15 |
| FR-RAW-024 | The system SHOULD allow the protocol developer to configure the execution context (e.g. dedicated thread vs. thread pool vs. user `SynchronizationContext`) per protocol instance. | Should | Configuration test: instance created with a dedicated thread, the callback is demonstrably executed on that thread. | Derived from the threading-model requirement |

#### 4.1.4 TX confirmation abstraction (TX confirm)

Background: State machines in L3/L4 (e.g. ISO-TP send path, CANopen SDO) need a reliable statement of when a frame was actually sent on the bus – not just that the driver accepted it. `ICanBus.Transmit` returns only the number of accepted frames (`ITransceiver.Transmit`), no send confirmation; echo support is optional (`CanFeature.Echo`).

| ID | Requirement | Priority | Verification | Source |
|---|---|---|---|---|
| FR-RAW-030 | The system MUST offer the protocol developer a uniform TX confirmation abstraction that works regardless of whether the underlying adapter supports hardware echo (`CanFeature.Echo`). | Must | Integration test against two adapter configurations (with/without `CanFeature.Echo`), each with a successful TX confirm callback. | Review, overall assessment "TX confirm abstraction"; `CanFeature.Echo` in `CanEnums.cs` |
| FR-RAW-031 | For adapters with echo support the system MUST use the actual send confirmation (echo frame) for the TX confirm and thereby correctly assign frames to the original send call by suitable criteria (e.g. ID + payload + sequence number/time window). | Must | Integration test (virtual loopback with echo enabled): N simultaneously sent, identical frames are correctly confirmed individually (no mis-matching). | Review §1.1 item 12 (`QueuedDeadline.Enqueue` crashes on identical frames) as negative example |
| FR-RAW-032 | For adapters without echo support the system MUST provide a documented approximation of the TX confirm (e.g. "accepted by the driver" as the best available confirmation) that communicates this difference explicitly to the caller (no silent pretence of a hardware confirmation). | Must | Unit test: the TX confirm result contains the confirmation kind (echo vs. driver acceptance); documentation check. | Derived from the "TX confirm" architecture gap |
| FR-RAW-033 | The system MUST report TX confirm failures (timeout, bus-off, rejection) to the caller as an observable result (e.g. failed future/task) instead of leaving the operation hanging indefinitely. A bus-off is reported as such when the adapter raises `ICanBus.FaultOccurred` while `ICanBus.BusState` reads `BusOff`; a fault in any other state leaves the send pending. No CanKit 0.5.6 adapter reports a bus-off that way (`src/CanKit.Pro.RawCan/README.md`, § *TX-Confirm*); there a send outstanding during a bus-off ends as a timeout (#348). The caller's cancellation token MUST be checked immediately before the driver call — on the echo path inside the send gate, i.e. after waiting behind another send's driver call —; a send cancelled by then ends with `OperationCanceledException`, and nothing reaches the driver (#294). | Must | Unit test: the TX confirm timeout scenario yields an error result within the configured deadline; a token cancelled before the call does not reach the driver on the approximated path (`TxConfirmTests.A_Token_Cancelled_Before_The_Call_Abandons_The_Approximated_Send`), one cancelled while waiting at the send gate does not on the echo path (`A_Token_Cancelled_While_The_Echo_Path_Waits_On_The_Gate_Abandons_The_Send`); a fault while `BusState == BusOff` resolves an outstanding confirmation as `BusOff` at once (`Outstanding_SendConfirmed_Resolves_As_BusOff_Immediately_On_Fault`), one in any other state does not (`A_Fault_While_The_Bus_Is_Not_Off_Leaves_The_Send_Pending`). | Review §1.1 items 8, 10 (hanging tasks in ISO-TP as negative example) |
| FR-RAW-034 | The system SHOULD allow the protocol developer to configure the TX confirm timeout per send operation. | Should | Configuration test: different timeout values lead to proportionally different failure times. | — |

### 4.2 L3 – Transport layer

#### 4.2.1 ISO-TP (ISO 15765-2)

As-is state (2026-09-15): shipped as `CanKit.Pro.IsoTp`. The following requirements describe the target behaviour; which of them are backed by a test is stated by `eng/verify-requirements-traceability.py`.

| ID | Requirement | Priority | Verification | Source |
|---|---|---|---|---|

| FR-TP-004 | The system MUST produce flow-control frames with the correct PCI type (`FC`, not `FF`) and without overwriting BS/STmin by padding. | Must | Unit test: the produced FC frame has PCI nibble `0x3`, the BS and STmin bytes match the values passed in. | Review §1.1 items 2, 3 |

## 7. Acceptance/Verification Strategy

| Test kind | Purpose | Applicable to | Prerequisite |
|---|---|---|---|
| **Unit test** | Isolated check of encoding/decoding logic, state-machine transitions, boundary values (e.g. STmin limits, PGN encoding, NRC mapping). | L2 (ownership, addressing), L3 (frame codec), L4 (service encoding) | No hardware needed; xUnit, existing matrix-test conventions (`tests/CanKit.Tests/Matrix/*`). |
| **Virtual-loopback integration test** | End-to-end behaviour via the existing `CanKit.Adapter.Virtual` without real hardware; standard procedure for CI. | L2 (demultiplexing, TX confirm, threading), L3 (ISO-TP/J1939-TP round trips), L4 (UDS/CANopen/J1939 sessions against a simulated peer) | Simulated peers (test ECU/node) based on the Virtual adapter. |
| **Fake-native test** | Adapter behaviour (L0/L1) without real vendor hardware via the `*.Fake.cs` layer (`-c Fake` configuration). | L1 (already established), indirectly L2/L3 where adapter-specific behaviour (echo, timeout) matters. | Existing fake configuration per adapter. |
| **Stress/concurrency test** | Uncovering data races, deadlocks, leaks under parallel load (several protocol instances, frequent subscribe/unsubscribe cycles). | L2 (threading model, registry), L3 (scheduler) | Repeated execution (N-fold), possibly with race-detection tools. |
| **Performance/timing test** | Measurement of jitter, throughput, STmin accuracy, idle CPU utilisation. | NFR-001..003, NFR-007 | Reference platforms (Windows, Linux; macOS for NFR-002). |
| **HIL test (hardware-in-the-loop)** | Validation against real ECUs/bus hardware for selected critical scenarios (e.g. real UDS diagnostic session, real CANopen device). | Sampled for L4 (UDS, CANopen, J1939) before production release. | Real test hardware, outside the standard CI run; see assumption A-5. |
| **Architecture/code review** | Checking requirements that cannot be tested automatically (documentation, conformance with the extension pattern, naming conventions). | FR-RAW-001, NFR-010, NFR-011 | Checklist, part of the PR review process. |

**Basic principle:** Every `Must` requirement MUST be covered by at least a unit or virtual-loopback integration test before the respective layer counts as "done". HIL tests complement this for production-critical L4 scenarios but, because of the hardware dependency, are not part of the standard CI gate. This rule has been checked mechanically since 2026-09-15: `eng/verify-requirements-traceability.py` reports every `Must` requirement no test mentions and runs as the CI job `requirements traceability` on every pull request. Two exemption lists in the script deliberately weaken the gate: `WAIVERS` names the requirements whose verification per this SRS is not a test (documentation/architecture review, CI matrix), `KNOWN_GAPS` the known `Must` requirements not yet backed by a test — a debt list that may only shrink. The job fails only on a new, unrecorded gap; a green run means "no new gap", not "every `Must` requirement backed". How many are open is stated by the script run — the number is deliberately not stated here so that it cannot go stale.
