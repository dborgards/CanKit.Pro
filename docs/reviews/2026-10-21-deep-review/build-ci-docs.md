### B-1 · The post-#314 release chain (SBOM assets, `attest` job) has never run, and 1.4.0 is waiting on it — Important, confidence high

`release.yml` and `.releaserc.json` were changed by PR #314 (`7607adb`, merged 2026-10-20T07:00Z): the `verify` job gained the SBOM generate/verify steps and the `packages` output (`release.yml:57-60, :149-160`), `prepareCmd` gained `verify-sboms.py` (`.releaserc.json:49`), the GitHub plugin attaches `*.cdx.json` (`:61`), and a new `attest` matrix job needs `id-token`, `attestations` and `artifact-metadata: write` (`release.yml:301-340`). `gh run list --workflow release.yml` shows the last run on 2026-09-30 — before all of this. What CI *does* cover: `eng/generate-sboms.py` and `eng/verify-sboms.py` run in the `pack (dry run)` job on every pull request (`ci.yml:214-223`) and are green on `36c97ca`. What nothing has covered: the artifact hand-over `verify → release` with the SBOM download (`release.yml:248-253`), `prepareCmd` with `${nextRelease.version}`, the asset upload, and the entire `attest` job — including whether `artifact-metadata: write` is accepted by the runner (the action's README does list exactly these three permissions, so it should be; YAML parses). The `attest` job is skipped on a dry run (`release.yml:304`), so even a dry run leaves it unexercised; its failure mode is benign and documented (`release.yml:297-300`: a release without attestations, re-run the job).

Meanwhile 26 `feat` and 199 `fix` commits sit on `main` unreleased; the next version resolves to 1.4.0. Mechanism of harm: the first real exercise of the new chain will be the 1.4.0 release, and a failure in `prepareCmd` aborts before the tag (fine), but a failure in the GitHub plugin's asset upload happens *after* `dotnet nuget push` and the baseline push — the "Option A" path of `docs/release-process.md:231-255`. Test: none possible in-repo. Fix: run `gh workflow run release.yml` with `dry_run=true` now (CLAUDE.md memory: "dry-run first"); it exercises `verify` end to end, the `release` job's artifact download and semantic-release's `verifyConditions`, `verifyRelease` (where `verify-release-config.mjs` runs) and `generateNotes` steps — but **not** `prepareCmd`: the pinned semantic-release 25.0.9 marks `prepare`, `publish`, `addChannel`, `success` and `fail` as `dryRun: false` (`lib/definitions/plugins.js`) and skips those steps in dry-run mode (`lib/plugins/normalize.js:34`). The `verify-packages.py` + `verify-sboms.py` hand-over check in `prepareCmd` therefore first runs at the real release. To have a dry run rehearse it, move it into `verifyReleaseCmd` next to `verify-release-config.mjs`; that step runs in dry-run mode. (Codex on #363 caught the overstatement.) Then cut 1.4.0 deliberately, while the diff is still in someone's head.

### B-2 · Ruleset bypass is `RepositoryRole 2` = *Maintain*, not the "repo-owner role" the docs describe — Docs, confidence medium

`gh api repos/dborgards/CanKit.Pro/rulesets/22609422`: `bypass_actors: [{actor_id: 2, actor_type: RepositoryRole, bypass_mode: always}]`. It works today because the owner (admin) outranks Maintain and semantic-release's pushes went through on 2026-09-30 — and, importantly, the two Write collaborators (`gh api .../collaborators`: `tom4711 write`, `Aparnaramesh-hawe write`) are *not* covered, so the gate holds for them. Confidence is medium because GitHub's own REST docs do not publish the id table; verify in *Settings → Rules → main-Branch → Bypass list*, which shows the role by name. Fix: either change the bypass to *Repository admin* (id 5) so the configuration says what the docs say, or correct the two texts to name the role actually granted. The docs sentence "only bypasses for that role, which the Actions bot does not hold" stays true either way.

### B-4 · `cancel-in-progress: true` also applies to pushes on `main` — Minor, confidence high

`ci.yml:13-15`: group `ci-CI-${{ github.ref }}`; on `main` the group is constant, so two merges in quick succession cancel the first merge commit's CI run (CodeQL has no `concurrency`, Docs uses `cancel-in-progress: false`). The second run tests a head that *contains* the first, so nothing is untested — but `git log --first-parent main` then has merge commits with a cancelled CI run, and a bisect or a "which commit went red" question lands on a run that never finished. Fix: `cancel-in-progress: ${{ github.event_name == 'pull_request' }}`.

### B-5 · GitVersion output is interpolated into `run:` scripts with `${{ }}` — Minor, confidence high (fact), low (exploitability)

`ci.yml:59, :89, :111, :125, :195, :217, :222` and `release.yml:114, :122-123, :139, :154, :160` paste `steps.gitversion.outputs.semver` / `needs.version.outputs.semver` / `steps.version.outputs.version` into shell text. The CI value is derived from the branch name by GitVersion (`GitVersion.yml:59-60`, label `pr`), i.e. from an untrusted pull-request head, including forks (`pull_request`, not `pull_request_target`, so the token is read-only and no secrets are reachable). GitVersion sanitises labels to `[A-Za-z0-9-]`, which is why this is not exploitable today; the release value comes from semantic-release on `main` only. The repository's own style elsewhere is the safer one (`release.yml:316` passes `VERSION` through `env:`). Fix: set `SEMVER: ${{ needs.version.outputs.semver }}` in `env:` and use `"$SEMVER"` in the scripts — one mechanical edit, no behaviour change.
