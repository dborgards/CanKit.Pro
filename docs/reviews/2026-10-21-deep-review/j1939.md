## 2. Status of previous findings (2026-09-30 review, main @ 8cec2ee)

### K1, J1939 half — fixed (PR #287, commits `c1dbb26`, `3199063`), RawCan half open (#249)

Marker lifecycle as implemented today, verified line by line:

- A marker is recorded before every Address Claim / Cannot Claim send, on the actor, when the bus is in Echo mode
  **or** merely declares `CanFeature.Echo` (`RecordClaimEcho`, `J1939NodeImpl.cs:1037-1044`; `BusEchoesOwnTransmits`
  `:872-873`, `BusMayFlagEcho` `:879-880`). Outside Echo mode the marker is `FlaggedOnly`.
- A `FlaggedOnly` marker is spent only by a frame the adapter flags (`TryTakeClaimEcho` `:1058`), so a peer's identical
  claim — never flagged — is still arbitrated. An Echo-mode marker is spent by any identical frame (`:1054-1068`).
- Bounded time: after a *confirmed* send a `FlaggedOnly` marker is put into the lingering state and given a
  `ClaimEchoGrace` (1 s, `:135`) by `NoteUnconfirmedClaimEcho(echo, mayStillEcho: true)` (`:998`, `:1387-1390`);
  a timed-out or bus-off send lingers likewise (`:684`, `:1383`); a rejected or throwing send drops the marker at once
  (`:1088-1093`, `:1006`, `:1394`). The grace callback retires the marker unless an identical *live* marker exists
  (`OnClaimEchoGraceElapsed` `:1127-1139`) — a live marker is a send whose `SendConfirmedAsync` has not returned, so the
  re-arm is bounded by the service's confirm timeout (1 s, `CanBusService.DefaultConfirmTimeout`). Residual: J-4 below.
- J11 (`_claimEchoGraces` growth): fixed in `3199063` — `ReleaseClaimEchoGrace` (`:1116-1122`) removes the handle when
  it fires or is replaced; `ClaimEchoGraceCount` seam `:1125`. Test `A_Fired_Claim_Echo_Grace_Handle_Is_Not_Kept`
  (`J1939NodeTests.cs:416`). The "endless 1 Hz re-arm" of the old finding needs a marker that is live for ever, which
  only J-4 produces.
- Third echo world: `EchoWorld.FlaggedNormal` (`EchoWorlds.cs:43`, `ControllableBus.FlaggedEchoInNormalMode` `:89-91`)
  is in `EchoWorldFixture.Both` (`:74`), so the four `[MemberData(Both)]` theories run it. Direct tests:
  `A_Peer_With_Our_Name_Is_Not_Spent_On_A_Flagged_Only_Marker` (`:443`), `A_Node_Does_Not_Arbitrate_Against_Its_Own_Name`
  (`:282`).

The RawCan half is still open: issue #249 is OPEN; `docs/upstream-candidates.md:90-92` records that PCAN in Echo mode
was *measured* delivering unflagged echoes (filed upstream as pkuyo/CanKit#71). On that configuration
`SendWithEchoConfirmAsync` cannot match (`CanBusService.cs:189`), the claim's confirmation comes back
`Confirmed=false, Timeout`, and `OnClaimAnnounceTxFailed` (`J1939NodeImpl.cs:677-705`) faults **every**

the failure is RawCan's, but the J1939 package is its most visible victim. Not re-rated here (other package).

### J9 — still present, never ticketed (Important)

`J1939NodeImpl.cs:1244-1252`: when `_transport.SourceAddress != sa` the send opens a single-use channel on the SA it
captured and runs a whole BAM/RTS session under it; `HasReclaimCrossed` (`:1285-1286`) throws only afterwards. The
branch is unreachable on the commit path (rebind happens-before `Claimed`), so it is reached only in the loss race:
a stronger peer's claim is processed on the actor between the gate (`:1206-1210`) and `:1244`, the actor rebinds to
0xFE, and the sender then transmits a full multi-frame session under an address J1939-81 says is the peer's.
No issue or commit mentions J9 (`git log --grep` empty, no open issue). No test reaches the branch; the previous
mutation j1939-M3 was green. Fix unchanged: replace the fallback with `throw new J1939NoAddressException()`.
Confidence: high (mechanism); the window is one actor turn, so frequency is low.

### J10 — still present, never ticketed (Minor, medium confidence)

## 3. New findings

### J-1 · The application-frame ledger never expires on a bus that does not echo, and keeps rejected sends — Minor, high

`SendCoreAsync` records every single-frame send in `_ownFrames` unconditionally (`J1939NodeImpl.cs:1225`), unlike the
claim markers, which are only recorded when an echo can come (`:1040`) and are dropped on rejection (`:1092`). A
`!Confirmed` send (`:1227`) leaves its entry; on a Normal-mode SocketCAN/Kvaser bus (no echo at all, #249 table) every
entry stays until 64 newer sends evict it. The entry matches by CAN ID *and* payload (`:1169-1183`), so it only bites
after the node has left that source address: a conforming peer that later claims the vacated SA and transmits a frame
with the same PGN, priority and payload — an all-0xFF "not available" payload on a standard PGN is the ordinary case —
is dropped once per retained entry as the node's own echo (`:1612`, `:1624`). Bounded (≤ 64 frames, once each) and
only after an address change, hence Minor. Test: `An_Echo_Dropped_By_The_Source_Address_Guard_Still_Leaves_The_Ledger`
(`:4135`) covers the three echo worlds only; nothing runs on `ControllableBus.Plain`.
Fix: give ledger entries the same bounded life as claim markers — drop on `Rejected`, and retire by a `ClaimEchoGrace`
armed when the confirmation returns without the echo having spent the entry.

### J-2 · A Request for Address Claimed directed at the preferred address is not answered while the node is Claiming — Minor, high

`HandleIncomingFrame` drops every PDU1 frame whose destination is not global while `myAddr < 0` (`:1627-1628`), and the
Request-for-Address-Claimed branch sits after that filter (`:1635-1639`). During the 250 ms window and during a backoff
the node holds no address (`:534`, `:785`, `:841`), so a Request for PGN 0xEE00 addressed to the address it is claiming
gets no answer, whereas a global one is answered by re-announcing (`:928-935`). SAE J1939-81 §4.2.2 (memory) does not
distinguish global from specific requests. Reachable by a conforming network-management tool that addresses the CA
whose claim it just saw. Fix: evaluate the request branch before the destination filter when
`da == _pendingClaim?.PreferredAddress`. No test (M4 gap).

### J-3 · Disposing during an automatic re-claim reports `ObjectDisposedException` as a background fault — Minor, high

The unseated node's automatic round creates a private TCS whose faulted continuation forwards to
`BackgroundExceptionOccurred` (`:833-835`). `DisposeCore` faults the pending claim with `ObjectDisposedException`
(`:1717`), so a `using` scope ending while an arbitrary-address node is moving after being unseated by a conforming
peer raises `ObjectDisposedException` through the background channel — the outcome the suite elsewhere asserts must not
happen (`A_Cannot_Claim_Handoff_That_Arrives_After_Dispose_Is_Dropped`, `:2133`, assertion `:2155`: "a disposed actor is not a failed
transmit"). Fix: exclude `ObjectDisposedException` (and `OperationCanceledException`) in that continuation. No test.

### J-4 · An Echo-mode claim marker whose echo is lost stays live for ever — Minor, low

On an Echo-mode bus a confirmed send's marker is not given a grace (`:998` is `FlaggedOnly` only). The echo normally
spends it, but the node's subscription is a 1024-deep `DropOldest` buffer (`CanBusService.cs:25`,
`Subscription.cs:86`): an echo dropped there under RX overload leaves a live marker permanently. Consequences: the next
peer claim with the same NAME on that address is swallowed once (`:1059-1062`), and any lingering sibling marker re-arms
its grace every second for ever (`:1133-1136`). Low: needs ≥ 1024 frames queued ahead of the echo. Fix: arm the grace
for every confirmed send whose marker is still unspent, not only `FlaggedOnly` ones. No test.

### J-5 · `ClaimAddressAsync` during an automatic move faults with advice the caller cannot follow — Minor, high

The automatic round after an unseat is registered as the claim in hand (`:844-845`), so a user `ClaimAddressAsync`
meanwhile faults with "await it, or cancel it, before claiming again" (`:364-371`) — but the automatic round hands out
no task and takes no token; the application can only poll `ClaimState` or wait for `AddressClaimChanged`. Reachable by
any conforming peer unseating an arbitrary-address node while the application re-claims. Fix: mark the unattended
`PendingClaim` and let `BeginClaim` sweep it (its outcome was "not asked for", `:829-832`), or document the wait.
Test `A_Claim_During_The_Backoff_Before_A_Reclaim_Faults_And_The_Reclaim_Completes` (`:1345`) pins the user-initiated
case only.

### J-6 · The arbitrary-address scan re-claims the address it just lost — Minor, medium

`TryGetNextArbitraryCandidate` (`:585-595`) records the *next* candidate as the scan start, so when the lost address
lies inside 0x80..0xF7 the scan wraps all the way round and claims it a second time before giving up: the exhaustion
test (`AddressClaim_ArbitraryFallback_ExhaustsField_ThenCannotClaim`, `:2514`) runs 121 rounds, not 120. One wasted
announcement + window + backoff per exhaustion, addressed to a stronger NAME that answers with a re-announce
(§4.4.3.3). Fix: seed `scanStart` with the lost address itself when it is in the field. The comments claiming 240
rounds (`:975`, test `:2522`) are wrong either way.

### J-7 · `_equalNameHeardOn` persists while no claim runs — Minor, medium (carried from §3)

Heard while NotClaimed, the observation lives until the next claim (`:756`; cleared only by `:543-544` for a different
address or `:1016-1017` on a non-Claiming transition). A claim of that address an hour later announces and then loses
at once (`:565-569`) even if the equal-NAME CA has long gone. The code documents the intent as "the race with a claim
queued behind that frame" (`:863-868`); a claim queued behind a frame is processed within one `ClaimAnnounceTimeout`,
so a timestamp and that bound would keep the intent and drop the memory. Test
`An_Equal_Name_Already_Heard_On_That_Address_Cannot_Claim` (`:1027`) pins the immediate case; none pins staleness.

### J-8 · `Reschedule` re-arms through a branch that can never succeed — Minor, high (no behavioural effect)

`_tick.Rearm(delay)` (`:1966`) is called on a deadline that has just fired; `Deadline.Rearm` returns false once the
state left Pending (`DeadlineScheduler.cs:133-134`), so every tick disposes the old deadline and allocates a new one.
The schedule works; the Rearm attempt and its comment are dead. Either arm fresh without the attempt, or (if the
allocation matters at high rates) make the actor timer re-armable. No test can observe it.

## 4. Test quality and gaps

The node suite is large and, for the claim state machine, unusually disciplined: wall-clock nodes are used only for
liveness, timing properties run on `VirtualClock` with `WaitUntilTimerArmedAsync` before every advance, and several
race windows are forced on the actor rather than sampled. Observations:

- Gaps with no test at all: J9 branch, J10 race, J-1 (non-echo world for the application ledger — no theory runs on
  `ControllableBus.Plain`), J-2/M4 (directed Request for Address Claimed, Claimed and Claiming), M5 (NAME AAC bit),
  M1 (overlap ban), M2 (coalescing), J-3, J-5 (user claim during an *automatic* move), PDU2 multi-frame with a specific
  destination (what `J1939Message` documents vs what `:1256` does), a rejected single-frame send's ledger entry.
- `AssertEqualNameContest` (`:1169-1183`) still accepts both "claim faulted" and "claimed then unseated" — unchanged
  since the previous review; it cannot tell a tie lost in the window from one lost afterwards.
- `ClaimAddressAsync_CancelAtArbitrationDeadline_NeverLeavesStateStuckInClaiming` (`:2903`) samples a 30 ms race 40
  times; it cannot fail falsely but may pass without reaching the interleave it exists for.
- `StartPeriodicSend_SingleFrame_StopsAfterAddressLoss` tolerates one slipped emission (`:4620`) — justified in the
  comment; it means a loop that emits exactly one stale frame per loss passes.
- SPN: indicator classification is pinned at every band boundary for 1/2/4/8/12/64-bit unsigned, 2/3/4/5/6/7-bit
  unsigned, 8/16-bit signed, and signed sub-byte (`J1939SpnIndicatorTests.cs`); `ExtractRaw`/`ExtractRawSigned` have a
  seeded differential test against a bit-by-bit reference and an argument-rejection sweep. Not covered: signed widths
  that are not 8/16 (e.g. 12-bit signed uses the leading byte at `:141-142`), `WriteRaw` beyond one hand-written
  round trip (`J1939NodeTests.cs:180`), `FromIndicator`'s argument validation, `J1939SpnValue.ToString`.

## 6. Doc drift

- `J1939NodeImpl.cs:975` and `J1939NodeTests.cs:2522`: "240 rounds" — the field has 120 addresses and the scan runs 121
  rounds (J-6).
- `IJ1939Node.cs:25-27`: "Disposal cancels any in-flight … `SendAsync` call" — not for single-frame sends; multi-frame
  sends fail with `ObjectDisposedException`, not a cancellation.
- `IJ1939Node.cs:94-95` and `J1939NodeImpl.cs:369-370`: "await it, or cancel it" — impossible for the automatic move
  (J-5).
- `J1939Message.cs:20-24, 39-41`: DA "ignored for PDU2 PGNs (always 0xFF on the wire)" — the multi-frame path routes
  on it (`J1939NodeImpl.cs:1256`).
- `J1939NodeException.cs:40-44, 51`: `J1939CannotClaimException` is documented for "a higher-priority peer … or the
  caller supplied only one candidate" (no such parameter exists) and its message always says "contested by a peer with
  higher-priority NAME" — it is also thrown for the equal-NAME tie (`:484` via `:907`) and for field exhaustion.
- `J1939NodeOptions.cs:54-58`: `ReceiveBufferCapacity` describes a receive buffer nothing exposes (J12).
- `J1939NodeOptions.cs:67`: `Validate` "called from `J1939Node.Open(ICanBus, …)`" — it is called from the
  `J1939NodeImpl` constructor for both overloads (`J1939NodeImpl.cs:180`).
- `J1939NodeImpl.cs:1518-1519`: "Dispose itself only cancels the bus subscription (fast)" — `J1939TpChannel.Dispose`
  joins its reader (≤ 2 s) and its own actor (≤ 5 s) on the node's actor; milliseconds normally, but not "only".
- README is consistent with the code on the claim procedure, the backoff, the request answer and the periodic grid.

## 7. What is done well

- Per-send claim-echo markers with identity (not content) and explicit lifetimes for every confirmation outcome; the
  `FlaggedOnly` rule makes the Vector-Classic-in-Normal-mode world safe without touching Echo-mode behaviour.
- The Cannot Claim ordering (fault only after the frame is handed to the driver, handoffs tracked per loss) is
  thorough and every branch of it has a scripted-bus test.
- Single-writer discipline is real: every state mutation is on the actor, cross-thread reads are `Volatile`, and the
  tests force interleavings on the actor instead of sampling them.
- `DisposeAsync` with the on-actor/off-actor split, one completion for concurrent callers, and failure reporting.
- SPN decoding: the `J1939SpnValue` return type, indicator bands per width with known-answer tests at every boundary,
  and a seeded differential test for bit extraction.

## 8. Open questions for the maintainer

1. #249 (RawCan half of K1): on measured PCAN hardware in Echo mode every J1939 claim fails at the confirmation. Until
   RawCan has a content-based fallback, should the J1939 README name PCAN + Echo mode as unsupported?
2. J9: replace the fallback channel with `J1939NoAddressException` (recommended), or is a send that captured its SA
   meant to finish on it?
3. J-5: should a user `ClaimAddressAsync` replace the automatic move (it is "the newer word") rather than fault?
4. Claim loss with a TP session in flight: `RebindTransportOnLoop` disposes the channel and `FailSessionsOnDispose`
   (`J1939TpChannel.cs:451-461`) fails the sessions without a TP.Conn_Abort, so the peer waits out T1/T3. An abort
   under the lost SA would itself be a violation; is the silent drop the intended answer, and should the node's docs say
   so?
5. J12: additive `ReadAllAsync`, or retire `ReceiveBufferCapacity` in 2.0 (#299)?
6. J-2: should a Request for Address Claimed directed at the preferred address be answered during the window?
