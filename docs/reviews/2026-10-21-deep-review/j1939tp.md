## 3. New findings

Severity order. "Reachability" uses the brief's three classes.

### T-1 · CM TX continuations are keyed by (destination, PGN), not by session instance — the T1 class of defect, on the other path

- **Where:** `J1939TpChannel.cs:1155-1156` (`onConfirmed: () => OnCmDtConfirmed(key, sn)`), `:1159-1162` (`OnCmDtConfirmed` looks the session up by key and filters only on `session.NextSn != confirmedSn`), `:1147-1149` (`TrySendNextCmDt(key)`), `:1236-1252` (T3/T4 expiry by key). Compare the BAM path after #258: `OnBamDtConfirmed(session, sn)` with `IsCurrentBamSession` (`:952-953`, `:1125-1128`).
- **Mechanism:** cancel a CM send while a TP.DT is unconfirmed (`CancelTxOnLoop` sends Abort(2) and `EndTx` removes the session, `:315-334`), send the same (destination, PGN) again at once (the key is released from `_admittedKeys` with the cancellation, so it is admitted and, with no other session to that destination, started immediately). If the peer's CTS for the new session arrives and the new session has sent its DT *n* before the old DT *n* confirmation arrives, the old confirmation passes the `NextSn == confirmedSn` check and advances the **new** session: `NextSn`, `BlockRemaining`, `HighestSentSn` move and `TrySendNextCmDt` hands DT *n+1* to a `Task.Run` while the new DT *n* is still unconfirmed — exactly the reordering the chain-on-confirmation discipline exists to prevent (`:1217-1219`). The new DT *n* confirmation is then discarded as "stale". Outcome if the pool reorders: the receiver aborts with code 7 and the send faults; not a silent success, unlike the BAM case was. The timer callbacks are safe: `CancelTxOnLoop` disposes the deadline (`:319`), and `FailOrRaiseTx` already checks `ReferenceEquals` (`:1274`).
- **Reachability:** API use (cancel + immediate resend of the same key) plus a TX confirmation that arrives later than the peer's CTS. On a real adapter the old DT precedes the abort and the RTS in the TX queue, so its echo normally precedes the CTS; the window needs a slow confirmation path. Narrow.
- **Severity:** Minor. **Confidence:** high for the mechanism (read against the BAM fix), low for frequency.
- **Test:** none. Mutation M-2 in §5 shows the stale-confirmation check has no test at all.
- **Fix:** give `TrySendNextCmDt`/`OnCmDtConfirmed`/`OnTxT3Expired`/`OnTxT4Expired` the `TxSession` instance and guard with the same `ReferenceEquals(_txSessions[key], session)` the BAM path uses (rename `IsCurrentBamSession` to `IsCurrentSession`); keep the SN check.

### T-2 · `BackgroundExceptionOccurred` is raised synchronously on the actor loop, and `AbortRx` raises it before the inbox fault is written

- **Where:** `AbortRx` (`:1366-1370`): `RaiseBackgroundException(ex)` then `_pduInbox.Writer.TryWrite(error)`. Other actor-loop raise sites: `HandleIncoming` catch (`:552`), `FailOrRaiseTx` (`:1283`), `OnActorBackgroundException` (`:1384`). `EmitPdu` (`:1333-1355`) does the opposite for the datagram path — inbox first, handler on the pool — precisely so a handler may wait on the channel (#58).
- **Mechanism:** a handler that blocks on this channel (a synchronous `ReceiveAsync().GetAwaiter().GetResult()` expecting the fault, a synchronous wait on a send) stalls the actor and with it every session and timer of the channel; in the `AbortRx` case the fault item it waits for is written only after the handler returns, so the wait never ends. The interface doc (`IJ1939TpChannel.cs:107-113`) says nothing about the thread the event runs on; `DatagramReceived`'s doc (`:97-105`) does, which invites the assumption that both behave alike. `J1939NodeImpl` only forwards the event (`J1939NodeImpl.cs:216`), so the node is not affected.
- **Reachability:** API misuse only.
- **Severity:** Minor. **Confidence:** high.
- **Test:** none; `DatagramReceived_Finds_The_Datagram_Already_Receivable` (2644) covers the datagram path only.
- **Fix:** in `AbortRx`, write the inbox item first and raise on the pool as `EmitPdu` does; or document the loop affinity on the event and leave it.

### T-3 · `ApplyPendingCts` does not clear `HoldPending`

- **Where:** `:1223-1234`; `HoldPending` is set at `:993-994` and cleared only by a CTS that grants packets (`:1002`) or when consumed at `:1205-1209`.
- **Mechanism:** early CTS for the next block stashed (`:1053-1061`), then a CTS(0) with `BlockRemaining == 1` sets `HoldPending`; at block end `HasPendingCts` wins (`:1197-1200`) and the next block starts with `HoldPending` still true; at *that* block's end, with no CTS yet, T4 (1050 ms) is armed instead of T3 (1250 ms). 200 ms shorter wait, abort reason unchanged.
- **Reachability:** only a non-conforming peer (CTS(0) after a grant it has not been served yet).
- **Severity:** Minor. **Confidence:** high.
- **Test:** none. Fix: `session.HoldPending = false;` in `ApplyPendingCts`.

### T-4 · `A_Cts_Hold_In_The_Middle_Of_A_Block_Is_Ignored` does not test what its name says

- **Where:** `J1939TpTests.cs:1616-1662`.
- **Mechanism:** the block it uses is the whole message (3 packets granted at once), so after the last DT the sender goes to `WaitEom` under T3 regardless of `HoldPending`. The condition `session.BlockRemaining == 1` at `:993` can be deleted (remember every mid-block hold) and the test stays green (mutation M-5). What the test pins is only "no T4 in `WaitEom`", which `A_Cts_Hold_While_The_Last_Packet_Is_Outstanding_...` (3426) already pins.
- **Severity:** Minor (test quality). **Confidence:** high (traced; not executed).
- **Fix:** grant 2 of 3 packets, hold while DT 1 is outstanding, release both DTs, and assert the timer armed at block end is T3, not T4.

### T-5 · A TP.DT with SN 0 is classified as "bad sequence" by a special case nobody tests

- **Where:** `:727-729`: `sn > 0 && sn < expected ? Duplicate : BadSequenceNumber`.
- **Mechanism:** correct (packet 0 does not exist, so 7 not 8, as the comment says), but no test injects SN 0; mutation M-6 would be green. Pure gap.
- **Severity:** Minor (gap). **Confidence:** high.

### T-6 · `ReceiveAllAsync` ends on the first reassembly abort; the doc says "same semantics as `ReceiveAsync`"

- **Where:** `IJ1939TpChannel.cs:90-96`; implementation `:358-367` (an exception thrown from `yield return UnwrapInboxItem(item)` finishes the iterator). `J1939NodeImpl.cs:1455-1476` knows this and re-enumerates in a loop, with a comment that records the earlier defect (#195) this caused in the node.
- **Mechanism:** a consumer that writes `await foreach (var d in channel.ReceiveAllAsync())` in a `try/catch` and continues after the catch has silently stopped receiving; the inbox and later datagrams are intact, only the enumeration is gone. `ReceiveAsync` is resumable, so "same semantics" is wrong on the one point that matters.
- **Severity:** Docs. **Confidence:** high.
- **Fix:** say in the doc that the abort ends the enumeration and the caller re-enumerates (as the node does), or catch the fault inside the iterator and raise it elsewhere — the former is the smaller change and matches the node's code.

### T-7 · The abort of a cancelled CM send can overtake its own RTS

- **Where:** `SendControlFrame` (`:1287-1328`) runs every frame in its own `Task.Run`; `CancelTxOnLoop` (`:326-327`) sends Abort(2) while the RTS's `Task.Run` may not yet have reached the driver.
- **Mechanism:** the pool does not order two queued work items. A peer that sees Abort then RTS opens a session nobody serves and holds it for T2 (1250 ms), then aborts it. Same shape for `AbortTx` racing an outstanding DT (harmless: the peer's session is being torn down anyway). Within a session, DTs are chained on confirmation, so this is confined to control frames that follow an unconfirmed one.
- **Reachability:** API use (cancel right after `SendCmAsync`) and pool scheduling. Rare; cost is 1.25 s of a blocked (SA, DA) slot on the peer.
- **Severity:** Minor. **Confidence:** medium (depends on whether `CanBusService.SendConfirmedAsync` serialises callers; not verified).
- **Fix:** send the abort from the RTS's confirmation continuation when the RTS is unconfirmed (as the BAM path waits for the announce confirmation before its first DT), or document.

### T-8 · `SendCmAsync` to the channel's own source address is accepted and times out

- **Where:** `SendCmAsync` (`:195-207`) validates only `destinationAddress != 0xFF`; the reader drops frames from its own SA (`:511`), so the peer never exists.
- **Severity:** Minor (API). **Confidence:** high. Fix: reject `destinationAddress == _sourceAddress` with `ArgumentOutOfRangeException`.

### What was checked and found sound (so the next review need not repeat it)

- **Timer table vs. code** (J1939-21 §5.10.2.4, from memory: Tr 200 ms, Th 500 ms, T1 750, T2 1250, T3 1250, T4 1050): originator T3 after RTS (`:936`), T3 after a block's last DT (`:1212`) and after the message's last DT (`:1187`), T4 after CTS(0) in `WaitCts` with re-arm on every repeated CTS(0) (`:997-998`), no originator timer while a block drains; receiver T1 after BAM (`:1622-1623`) and per DT (`:1670-1688`, `Rearm` with a fresh `Arm` fallback), T2 after every CTS (`:666`, `:784`). All four defaults match the table. Tr and Th are not timers of this stack, and the README says why.
- **Retransmit frontier and the 255 wrap:** `HighestSentSn` is an int, `frontier`/`expectedSn` are computed in int (`:1013-1015`), `NextSn` wrapping to 0 after packet 255 never reaches `TrySendNextCmDt` (the only paths out of a confirmed packet 255 are `WaitEom` or a stashed retransmit, which rewrites `NextSn`). `numPackets > totalRemaining` (`:1040-1047`) keeps `BuildDt` from ever seeing an offset past the PDU. Covered by `A_Retransmit_Request_For_The_Last_Of_255_Packets_Is_Served` (2617) and the four #152 tests.
- **RX sequence validation:** exact-match on `NextExpectedSn` (`:717`), SN 255 is always the last packet because `IsValidTotals` pins `totalPackets == ceil(bytes/7) <= 255` (`:814-819`), the copy length is bounded by the buffer (`:744-747`), and a frame shorter than 8 bytes never reaches the actor (`:480`).
- **Bounds ≥ 1786:** send side `ValidateSendPayload` (`:279-281`); RTS with `totalBytes > 1785` answered with code 9, other malformed totals ignored (`:627-639`); malformed BAM ignored without superseding (`:585-586`, test 1103).
- **Abort frame contents:** control 0xFF, reason, 0xFF ×3, PGN LE (`J1939TpFrames.cs:132-143`); every emitted reason is a table-7 code, and the receive side surfaces whatever byte arrives (`:682`, `:1106`). Pinned by `Abort_Reason_Goes_On_The_Wire_As_Table_7_Assigns_It` (1983).
- **BAM spacing-timer release:** `EndTx` (every normal end, cancel, abort, TX failure via `FailOrRaiseTx`) and `TxSession.Fail` (dispose) both call `ReleaseSpacingTimer`; `TxSession.Cancel` is unused (`570ab7b`). Nothing else ends a BAM session.
- **Admission under cancellation:** a token cancelled between the `IsCancellationRequested` check and `Register` runs the callback inline, which posts `CancelTxOnLoop` ahead of `BeginTxOnLoop`; `BeginTxOnLoop` then sees a completed TCS and returns (`:833-834`). `RemoveQueued` is O(1) and a no-op for a non-queued entry; `EndTx` skips completed heads (`:912-915`); `ReleaseSlot` runs exactly once per completion under the same lock as `Admit` (`:1457-1501`). Six tests from #215 pin this (2784-3281).
- **Dispose ordering:** reader joined and subscription disposed before the sessions are failed; `HandleIncoming` drops late posts; an owned actor's `Dispose` runs the posted cleanup in `FinalDrain` before the owned service is disposed (`ProtocolActor.cs:617-632`).

## 7. What is done well (brief)

- The #258 fix is the right shape: session identity carried in the closure plus the handle held on the
  session, with one test per line of defence and two tests that fail only without both.
- The retransmit model (`HighestSentSn` frontier vs. `NextSn` cursor, `AllPacketsSent` for the EOM)
  is small, commented with the review that forced each rule, and pinned by five tests.
- `TxCompletion` makes "slot back" and "outcome published" one step under one lock; the seam that
  tests it is two lines.
- Dispose on a borrowed actor is thought through in all four cases (free, busy, from its loop, gone)
  and each case has a test.
- The README says what is and is not validated, in the first paragraph.

## 8. Open questions for the maintainer

1. **T3 (bidirectional abort):** which J1939-21 revision is the reference? If it defines the
   Connection Abort Role in byte 3, the fix is to send and read it; if not, the only safe behaviour
   is to apply a peer abort to the direction its PGN uniquely identifies and, when both match, to
   both — which is what the code does today and could simply be documented.
2. **T-2:** should `BackgroundExceptionOccurred` move off the actor loop like `DatagramReceived`
   (behaviour change, `fix:`), or be documented as loop-affine (`docs:`)? ISO-TP and the CANopen
   node should answer the same way, so this is a cross-package decision.
3. **T-6:** doc fix only, or make `ReceiveAllAsync` survive an abort (behaviour change the node would
   then no longer need its re-enumeration loop for)?
4. **Codes 4 and 6:** accept that this stack never sends them (liberal receiver, stashed early CTS)
   and say so in the enum doc, or add the checks? The stash exists for a race a real bus can produce
   too (the receiver's next CTS can arrive before the originator's own DT confirmation), so sending 4
   would need the confirmation to gate it.
5. **§4 CM round trips on the real clock:** extend #279's treatment (`PacedRoundtripOptions`-style
   lifted T1/T2/T3) to the CM round trips, or leave them as the suite's canaries for #277-type stalls?
